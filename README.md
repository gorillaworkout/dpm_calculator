# Dupoin DPM Tools

D&W Calculator plus Deal Segregator, PL by Desk and Segregated for the DPM Malaysia team.

GitHub: https://github.com/gorillaworkout/dpm_calculator

## D&W Calculator — auto hitung Handling Fee, Xero Rate, Xero USD, Forex Gain/Loss

Jalan di **macOS maupun Windows**. Yang menghitung adalah `hitung_dw.py`
(Python, lintas-platform). File launcher-nya beda per OS:

| File | OS | Cara pakai |
|---|---|---|
| `Hitung DW.app` | macOS | double-click → pilih file Excel |
| `Hitung DW.bat` | Windows | drag file Excel ke file .bat, atau double-click lalu drag |
| `Hitung DW.command` | macOS (cadangan) | klik kanan → Open With → Terminal |

Paket ini **khusus macOS** — hanya `Hitung DW.app` (+ `Hitung DW.command` sebagai
cadangan). Semua file `.py`-nya sendiri lintas-platform dan tidak bergantung macOS,
jadi untuk dipakai di server atau website cukup panggil `hitung_dw.py` langsung.
| `hitung_dw.py` | dua-duanya | lewat Terminal / Command Prompt |

## Setup Windows (sekali saja)

1. Download Python: <https://www.python.org/downloads/windows/>
2. Saat install, **CENTANG "Add python.exe to PATH"** (ini yang paling sering kelupaan).
3. Buka **Command Prompt**, jalankan:
   ```
   py -m pip install openpyxl
   ```
   **Pakai `py -m pip`, jangan `pip` saja.** Kalau `pip install openpyxl` menghasilkan
   `'pip' is not recognized as an internal or external command`, itu bukan berarti Python
   gagal terinstall — folder `Scripts` milik Python saja yang belum masuk PATH.
   `py -m pip` tidak butuh itu karena `py` dipasang langsung ke `C:\Windows`.
   Kalau `py` juga tidak dikenali: tutup semua Command Prompt dan buka yang baru
   (PATH tidak ter-refresh di jendela yang dibuka sebelum install).

   Langkah ini boleh dilewati — `Hitung DW.bat` otomatis memeriksa openpyxl
   dan menawarkan menginstallnya.
4. Copy seluruh folder `dw-calculator` ke Windows, mis. ke `C:\dw-calculator`.
5. Double-click `Hitung DW.bat`.

Kalau muncul `Python belum terpasang / belum masuk PATH`, ulangi langkah 2
(install ulang Python dan centang kotak PATH-nya).

```bash

```

`pdfplumber` reads the FinanceOS PDF for PL by Desk and does not need poppler.
`poppler-utils` (`pdftotext -layout`) is only a fallback, used when pdfplumber
is not installed.

### Version (`VERSION`)

The footer of every page, error/STOP messages, and `GET /version` (login
required) show the running version, for example `DW Calculator v1.36 · 2026-11-03`.
It comes from the `VERSION` file at the repo root, read once when the app starts.
The server has no `.git`, so the version cannot come from git.

**Bump `VERSION` in every PR:** `version=1.<PR number>`, `build=<YYYY-MM-DD>`.
Do not put a commit SHA in it. Copy `VERSION` with the other files on every
deploy and restart the app. A missing file shows `version unknown`.

### Upload log (`/upload/*`)

Every `/upload/*` request writes one line to stderr (the pm2 error log), for
example:

    upload 2026-10-21T11:40:12+07:00 POST /upload/chunk 200 bytes=10486123 ms=812 id=1a2b… file=0 seq=0 ip=203.0.113.9 user=kvb-ops

`ip` is `CF-Connecting-IP` (cloudflared connects from 127.0.0.1). A `note=` is
added for a re-sent chunk that was already stored, an out-of-order chunk, a short
or cut-off body (`408`, the browser retries), and a request that raised. File
contents are never logged. To check an incident: `grep '^upload ' <pm2 error log>`.
If no line exists for a chunk the browser says it sent, the request never reached
gunicorn (network, firewall, antivirus, or Cloudflare).

### Tests (`test_*.py`, v1.36)

Every test is a plain script; run them all from the repo root:

```bash
for t in test_*.py; do python3 "$t" > /dev/null 2>&1 && echo "ok   $t" || echo "FAIL $t"; done
```

(or one at a time, e.g. `python3 test_app.py`). The suite is self-contained and
must be green on a fresh checkout, on the server and on a laptop:

- **Own temp users DB, session key and jobs dir.** Each test calls
  `testkit.hermetic_env()` before `import app`; it *assigns* `DW_AUTH_DB`,
  `DW_JOB_DIR` and `DW_ADMIN_*` to a fresh temp dir (removed at exit), so an
  exported server env never leaks in. `testkit.assert_isolated()` then proves
  the app uses only that temp dir. Tests never read or write the real
  `users.db` or `session.key`.
- **Synthetic fixtures only.** Deals History CSVs, Equity FX, the DPM D&W
  source, `Template D&W.xlsx` (built with `buat_template.py`) and the PL by
  Desk FinanceOS PDF/Excel + Metabase workbook are generated by `testkit.py`.
  No client file is needed or committed.
- Needs the packages in `requirements.txt`; `test_upload_retry.py` also needs
  `node` to check the browser JavaScript. The `MT4 real-file` checks in
  `test_deal_segregator_mt4_*.py` are optional extras that run only when the
  private files are present (`MT4_ACCOUNT_TYPES`, …); the synthetic checks in
  the same files always run.

Deploy note: copy `testkit.py` together with the `test_*.py` files.

## Bulan laporan — `--period` / dropdown di web app

Ekspor back office **selalu punya ekor**. File "Juni" yang diunduh dari back office
biasanya berisi **25 Mei s/d 5 Juli**: ekspornya disaring pakai *Apply Date*,
sementara laporan ini dibangun di atas *Paid Date* (deposit) dan *Completed Date*
(withdrawal). Kalau ekor itu ikut, `MTOATD` keluar 42 blok tanggal bukan 30, dan
totalnya memuat uang bulan lain.

Di web app ada dropdown **Report month** yang **wajib** diisi (default: bulan lalu).
Lewat Terminal:

```bash
python3 isi_template.py "sumber.xlsx" --bulan 2026-06 -o kerja.xlsx
python3 hitung_dw.py    "kerja.xlsx"  --period 2026-06
```

Basis tanggalnya sama dengan yang dipakai seluruh laporan — kolom `Date` per baris,
yaitu `Paid Date` untuk sheet `D` dan `Completed Date` untuk sheet `W` — jadi satu
baris masuk bulan yang sama di `D&W Report`, `MTOATD` dan `Payment Channel Balance`.
Yang ikut disaring: sheet **D**, sheet **W**, dan **Fund Transfer Table**
(J Wallet + kolom *Fund transfer* di Payment Channel Balance).

Baris yang dibuang **tetap ada** di sheet D/W, hanya 4 kolom hitungannya dikosongkan
dan diarsir abu-abu — filter `(Blanks)` untuk melihatnya. Rinciannya di sheet
`Missing Data` bagian **0**, aturannya di sheet `Legend` bagian **REPORT MONTH**.

Kalau tidak ada satu pun baris yang cocok, tool **berhenti** dan menyebut bulan apa
saja yang sebenarnya ada di file itu. Sengaja gagal: workbook kosong yang kelihatan
normal lebih berbahaya daripada pesan error.

Tanpa `--period`, semua tanggal dihitung (perilaku lama) dan itu ditulis merah di
sheet `Legend`.

Terbukti pada file uji 38 MB (`June - ..._Test 1.xlsx`, 25 Mei – 5 Jul):

| | tanpa `--period` | `--period 2026-06` |
|---|---|---|
| baris dihitung | 168.732 | 128.210 |
| blok tanggal MTOATD | 42 (25 Mei – 5 Jul) | **30 (Juni saja)** |
| baris dibuang | – | 40.901 (D: 17.805 Mei + 7.177 Jul; W: 11.114 Mei + 4.804 Jul + 1 tanpa tanggal) |

## Yang dihitung

4 kolom baru di kanan sheet `D` (dan `W` kalau ada):

| Kolom | Rumus | Format |
|---|---|---|
| Handling Fee | `Transaction × rate` dari sheet `D&W FEE`, dicocokkan Currency + Payment Gateway. Deposit pakai kolom Deposit, withdrawal pakai kolom Withdrawal (dibaca dari kolom `Source Name` tiap baris) | `#,##0.##` → `8,100`, `0.18` |
| Xero Rate | kurs di sheet `XERO` pada `Paid Date` + `Currency`. Kuning = tanggal belum ada di XERO, dipakai kurs tanggal terdekat sebelumnya | `#,##0.######` → `26,317.2`, `61.5507`, `1` |
| Xero USD | `Transaction ÷ Xero Rate` | `#,##0.00` |
| Forex Gain/Loss | deposit: `Xero USD − USD` · withdrawal: `USD − Xero USD` (tanda dibalik karena uang keluar — atur di `FLIP_FOREX_ON_WITHDRAWAL`) | `#,##0.00` |

### Sheet yang dihasilkan

| Sheet | Isi |
|---|---|
| `D` / `W` (dan sheet transaksi lain) | data aslimu + 4 kolom hitungan, ditandai warna. Kalau file sudah punya kolom `Handling Fee` / `Xero Rate` / `Xero USD` / `Forex Gain/-Loss` / `Currency Gain/Loss`, **kolom itu yang diisi** — judulnya tidak diubah, jadi tampilan file tetap sama |
| **`D&W Report`** | **ringkasan Currency × Payment Gateway, layout sama dengan report D&W yang sudah beredar** — bagian Deposit di atas, Withdrawal di bawah, masing-masing dengan Grand Total |
| `D&W Detail` | tabel datar gabungan semua sheet transaksi, satu baris per transaksi + kolom audit |
| `Missing Data` | rincian data yang belum ada: tanggal kurs yang tidak ada di `XERO` (per currency, per tanggal, berapa baris, kurs tanggal berapa yang dipakai, selisih berapa hari), rate fee yang belum ada, masalah data lain |
| `Legend` | penjelasan kolom & arti warna (English) |

Keempat sheet hasil **ditulis ulang tiap run** — jangan diedit manual.
Matikan semuanya dengan `--no-report`.

#### Sheet `D&W Report` — rumusnya

Dikelompokkan per `Currency` → `Payment Gateway`, memakai nilai **apa adanya**
(spasi di ujung nama gateway tidak dibuang, supaya `TRC20` dan `TRC20 ` tetap
terpisah seperti di pivot Excel).

**Bagian Deposit**

| Kolom | Rumus |
|---|---|
| `CRM USD ` | jumlah `USD` |
| `TRANSACTIONS` | jumlah `Transaction` |
| `Xero USD ` | jumlah `Xero USD` |
| `Total FE Gain/-Loss (USD)` | `Xero USD − CRM USD` |
| `CRM Average Rate` | `TRANSACTIONS ÷ CRM USD` |
| `Xero average Rate` | `TRANSACTIONS ÷ Xero USD` |
| `Recorded in Xero` | dikosongkan — diisi manual |
| `Rounding Adjustment` | `−Xero USD` |

**Bagian Withdrawal** (ada satu kolom tambahan, `Handling Charges Income`)

| Kolom | Rumus |
|---|---|
| `CRM USD ` | jumlah `USD` |
| `Handling Charges Income` | jumlah kolom `Charges` dari sheet `W` |
| `Transactions` | jumlah `Transaction` |
| `Xero USD ` | jumlah `Xero USD` |
| `Total FE Gain/-Loss (USD)` | `CRM USD − Xero USD` (tanda berlawanan dengan deposit) |
| `CRM average` | `Transactions ÷ CRM USD` |
| `Xero average` | `Transactions ÷ Xero USD` |
| `Recorded in Xero` | dikosongkan — diisi manual |
| `Rounding Adjustment` | `+Xero USD` |

**KVB: kolom basis Settlement Date (v1.30, `--settlement-columns`)**

Hanya untuk KVB (`KVB_ARG` di `app.py`: `isi_template.py --settlement-rows` +
`hitung_dw.py --settlement-columns`). DPM tidak berubah.

Deposit: `A Currency | B Payment Gateway | C CRM USD (Paid Date) | D CRM USD (Settlement Date) |
E TRANSACTIONS (Paid Date) | F TRANSACTIONS (Settlement Date) | G Xero USD | H Total FE Gain/-Loss (USD) |
I CRM Average Rate (Paid Date) | J CRM Average Rate (Settlement Date) | K Xero average Rate |
L Recorded in Xero | M Rounding Adjustment` — biru-kelabu A–G, hijau H–M.

Withdrawal: `A | B | C CRM USD (Completed Date) | D CRM USD (Settlement Date) |
E Handling Charges Income | F Transactions (Completed Date) | G Transactions (Settlement Date) |
H Xero USD | I Total FE Gain/-Loss (USD) | J CRM average (Completed Date) |
K CRM average (Settlement Date) | L Xero average | M Recorded in Xero | N Rounding Adjustment` —
biru-kelabu A–H, hijau I–N.

| Kolom | Rumus |
|---|---|
| `CRM USD (Settlement Date)` | jumlah `USD`, baris finish/success yang `Settlement Date`-nya di bulan laporan |
| `Transactions (Settlement Date)` | jumlah `Transaction`, basis yang sama |
| `CRM average (Settlement Date)` | `Σ Transactions (Settlement) ÷ Σ CRM USD (Settlement)`, kosong kalau 0 |

- Basis Settlement **ikut memuat** baris yang Paid / Completed Date-nya di bulan
  depan (atau bulan lalu) asal ada di file. `isi_template.py --settlement-rows`
  menyalinnya (tanpa menggeser saldo pembuka); `hitung_dw.py` memakainya **hanya**
  untuk kolom Settlement — records, pivot lama, MTOATD, Channel Balance, J Wallet,
  D&W Detail tetap sama persis (lihat catatan 3 Sep 2026 di `process_sheet`).
  Di sheet D/W baris itu tetap ada, kolom hitungannya kosong/abu-abu.
- `Settlement Date` kosong → hanya di basis lama, dilaporkan di Missing Data 7b.
- Rebate Withdrawal memakai `Settlement Date`-nya sendiri.
- Xero USD, FE, Xero average, Recorded in Xero, Rounding, Handling Charges tetap basis lama.
- Gateway yang hanya ada di basis Settlement dapat baris sendiri (kolom lain 0).
- Missing Data bagian 7: daftar baris khusus Settlement (7a), Settlement kosong (7b),
  Settlement di bulan lain (7c), dan cek deposit Settlement USD vs MTOATD CRM入金
  per currency (7d, informasi; selisih yang tidak terjelaskan = peringatan).
  Date Check menghitungnya sebagai "kept for Settlement Date columns only".

**KVB: Balance (USDT) di Payment Channel Balance (v1.32, `--cny-balance-usdt`)**

Hanya untuk KVB (`KVB_ARG` di `app.py`). DPM tidak berubah: tanpa flag, sheet
Payment Channel Balance tetap 11 kolom.

- Sumber rate: sheet **`CNY RATE`** di file upload KVB yang sama, kolom
  `Date | TD | Rate` (Rate = CNY per 1 USDT, mis. 6.74). Nama sheet dan header
  tidak peka huruf besar/kecil dan spasi (`cny rate`, ` DATE `). TD dicocokkan
  ke gateway lewat `kunci_channel` (`chip pay` = `ChipPay` = `CHIPPAY`). Tanggal
  boleh tanggal Excel atau teks (`2026-07-01`).
- Tiga kolom disisipkan di antara `Balance` dan `Status` pada **setiap baris CNY**
  (saldo pembuka dan harian): `CNY Rate`, `Balance (USDT)` (= Balance ÷ rate,
  disimpan sebagai nilai), `Rate source`. Baris non-CNY dan blok USD(CNY) kosong.
  Header: kolom data `ACB9CA`, kolom hitungan hijau (sama dengan D&W Report).
- Tanggal tanpa rate → rate tanggal sebelumnya yang terdekat, ditandai
  `(carried)`; kalau tidak ada → tanggal sesudahnya yang terdekat, `(carried back)`.
  Baris pembuka memakai rate pertama di periode. Rate 0 / negatif / teks →
  sel dikosongkan (tidak diisi diam-diam). Gateway tanpa rate → kosong + catatan.
  Rate < 1 dipakai apa adanya tapi dicatat (curiga USDT per CNY). Tanggal dobel:
  rate pertama dipakai, yang beda dicatat.
- Sheet tidak ada → run tetap jalan, kolom kosong, peringatan di log dan
  Missing Data (plus petunjuk kalau sheet lain punya header Date | TD | Rate).
- Missing Data bagian 8: gateway tanpa rate & TD yang tidak cocok (8a), tanggal
  yang memakai rate tanggal lain / dikosongkan (8b), baris CNY RATE yang tidak
  dipakai apa adanya (8c). Legend punya bagian "CNY BALANCE IN USDT".
- `siapkan_kvb.py` dan `isi_template.py` membawa sheet `CNY RATE` ke file hasil.

Judul, label, warna header, fill, format akuntansi, dan lebar kolom disamakan
dengan report aslinya. Periode di bawah judul bagian diambil dari bulan yang
paling banyak muncul di data — atur manual dengan `--period 2026-06`.

**Urutan grup** tidak bisa direproduksi dari report lama (urutannya tersimpan di
cache pivot Excel). Atur dengan `REPORT_GROUP_ORDER` di config:
`"value"` (default, CRM USD terbesar dulu), `"appearance"` (urutan kemunculan di
sheet), atau `"alpha"` (A–Z).

### Sheet `Legend` di file hasil
Tiap run, file hasil dapat sheet **`Legend`** berisi penjelasan keempat kolom
dan arti setiap warna, **dalam bahasa Inggris**, lengkap dengan contoh sel berwarna.
Sheet ini ditulis ulang setiap run, jadi jangan diedit manual.
Penjelasan yang sama juga terpasang sebagai komentar di sel header kolomnya
(arahkan kursor ke header `Handling Fee` / `Xero Rate` / dst).

### Arti warna sel
| Warna | Kolom | Arti |
|---|---|---|
| **Merah** `Handling Fee` | rate Currency + Payment Gateway belum ada di tabel fee. Sel sengaja **dikosongkan, bukan 0**, supaya tidak terhitung diam-diam. Tambahkan barisnya di sheet `D&W FEE` lalu hitung ulang |
| **Merah** `Xero Rate` / `Xero USD` / `Forex` | kurs tidak ditemukan sama sekali untuk tanggal + currency itu |
| **Kuning** `Xero Rate` | tanggalnya belum ada di sheet `XERO`, dipakai kurs tanggal terdekat sebelumnya. Lengkapi sheet XERO untuk menghilangkannya |

Keterangan ini juga terpasang sebagai komentar di sel header masing-masing kolom di Excel.

Baris `<CURRENCY>/Other` di tabel fee **hanya** dipakai kalau nama gateway di data
memang literal `Other`. Gateway lain yang tidak ketemu dibiarkan merah — jadi tidak
ada lagi rate yang diam-diam dianggap 0%.

### Kolom tanggal untuk cari kurs
Dicari berurutan sesuai `DATE_COLUMNS`: `Paid Date` → `Completed Date` → `Settlement Date` → `Apply Date`.
Sheet `D` punya `Paid Date` → dipakai. Sheet `W` tidak punya → turun ke **`Completed Date`**.
Kolom yang benar-benar dipakai selalu dicetak di laporan tiap run.

### Tanggal withdrawal kosong / teks / 1970 — fallback per baris (`tanggal_util.py`, v1.28; Rebate v1.29)
Sebelumnya `isi_template.py` dan `hitung_dw.py` hanya melihat **satu** kolom
(`Completed Date`). Baris Rebate Withdrawal yang `Completed Date`-nya kosong, teks
(`success`) atau 1970 — padahal jamnya ada di `Completed Time` — dibuang diam-diam
(Sep 2026: ±101.000 baris), dan sheet *Missing Data* tetap menulis "None".

Sekarang kedua script memakai **satu** fungsi (`tanggal_util.tentukan_tanggal`, juga untuk
jalur KVB karena KVB menjalankan script yang sama). Urutan per baris, sheet `W`:

1. `Completed Date` kalau tanggal sah (1990–2100). **Menang atas kolom lain**, termasuk
   baris backfill yang `Completed Time`-nya jauh lebih lama (dicatat sebagai "disagrees",
   bukan ditimpa). Mau sebaliknya? ganti `UTAMAKAN_WAKTU = True` di `tanggal_util.py`.
2. Kalau kosong / teks / tahun di luar 1990–2100: bagian **tanggal** dari `Completed Time`
   (datetime atau serial Excel > 1000; jam saja tidak dihitung).
3. Lalu `Settlement Date` — **kecuali** `Completed Date` memang 1970 (artinya "belum dibayar"):
   itu hanya boleh diselamatkan lewat `Completed Time`.
4. `Apply Date` **tidak pernah** dipakai (bisa jatuh di bulan yang salah).

#### Rebate Withdrawal — `Completed Date` diabaikan (v1.29)
Untuk baris yang `Source Name`-nya **`Rebate Withdrawal`** atau **berakhir dengan** itu, mis.
`08-2026 Rebate Withdrawal` (huruf besar/kecil dan spasi diabaikan), `Completed Date` **bukan** tanggal selesai yang asli: hanya 3.593 baris yang
mengisinya (semua Sales UID 100007), 32 tanggal 1 Agu–1 Sep 2026 pada baris yang diajukan
2024–2026 (median 308 hari sesudah `Apply Date`, bahkan sebelum `Apply Date` di 190 baris).
`Completed Time` bisa dipercaya (dalam 1 hari dari `Apply Date` di 104.159 dari 104.815 baris).
Maka untuk Rebate urutannya jadi:

1. **`Completed Time`** (datetime / serial Excel > 1000).
2. **`Settlement Date`**.
3. `Completed Date` **tidak dipakai**; `Apply Date` tetap **tidak pernah** dipakai.

`Withdrawal` biasa dan sumber lain **tidak berubah** (aturan v1.28 di atas, termasuk
`UTAMAKAN_WAKTU`). `Source Name` kosong / tidak berakhir dengan kata utuh `rebate withdrawal`
(mis. `Withdrawal`, `08-2026 Withdrawal`, `Rebate`, `Rebate Withdrawals`, `Unrebate Withdrawal`)
→ aturan v1.28. Untuk KVB, `siapkan_kvb.py` juga menyeragamkan `MM-YYYY Wallet withdrawal` /
`MM-YYYY Rebate Withdrawal` → `Rebate Withdrawal` (supaya rumus MTOATD Wallet出金 ikut cocok). Satu fungsi yang sama dipakai `isi_template.py`,
`hitung_dw.py` (saringan ulang) dan MTOATD, jadi ketiganya selalu sepakat. Baris yang
Completed Time-nya jatuh lewat tengah malam (apply 30 Sep, selesai 00:00:20 1 Okt) masuk
**Oktober** — memang begitu. Sheet **Date Check** menambah baris
`Rebate Withdrawal: Completed Date ignored, date taken from` (per kolom) dan
`Completed Date ignored for Rebate` (jumlah baris yang `Completed Date`-nya beda > 3 hari dari
`Completed Time`; hanya informasi).

Sheet `D` (`Paid Date`) tidak berubah. Baris yang masih tanpa tanggal tidak masuk bulan
mana pun, tetapi **dihitung dan dilaporkan**: sheet **Date Check** dan bagian *0b* di
**Missing Data** memuat baris dibaca / dipakai, dilewati per bulan (di luar bulan laporan),
dilewati karena tanggal kosong / tidak sah / 1970, jumlah yang tanggalnya diambil dari
kolom cadangan, dan konflik `Completed Date` vs `Completed Time`. Kalau > 1% baris sebuah
sheet tidak punya tanggal, muncul baris **WARNING** (workbook + log job web).
Ekspor Rebate yang kolomnya bergeser (kata `success` di `Pay Channel`) ditandai di log
dan Date Check; `Status` tetap dibaca dari kolom `Status` (kalau kosong dan ada kata status di
`Pay Channel`, kata itu yang dipakai).
Tes: `test_tanggal_fallback.py`.

## File lambat? Rapikan dulu — `rapikan_file.py`

```bash
python3 rapikan_file.py ~/Downloads/"DPM-D&W.xlsx" --buang-pivot
```

Dua sumber pemborosan yang dibersihkan, keduanya tidak kelihatan dari Excel:

| Penyebab | Contoh nyata di `DPM-D&W.xlsx` |
|---|---|
| **Baris hantu** — baris kosong yang pernah diformat | sheet `D` tercatat 918.498 baris, isinya 182. `sheet2.xml` = 178 MB |
| **Pivot cache** — salinan data sumber PivotTable | 28,7 MB. Menyumbang **99,8%** waktu buka |

Hasil terukur:

| | Sebelum | Sesudah |
|---|---|---|
| ukuran file | 20,7 MB | **0,2 MB** |
| waktu buka (openpyxl) | 313 detik | **0,2 detik** |

### Rumusnya

Semua ada di `mtoatd_spec.py`. Per tanggal `t`, per currency:

```
MT4入金            = Σ USD          [Settlement Date = t]
Wallet入金          = (tidak ada rumusnya -> KOSONG)
CRM入金            = MT4入金 + Wallet入金
TD入金             = Σ USD          [Paid Date = t]
——crm已入,TD未入    = Σ USD          [Settlement = t, Paid > t]
——调上日差异 (入金)   = -Σ USD         [Paid = t, Settlement < t]
MT4出金            = Σ USD          [Settlement = t, Source Name = 'Withdrawal']
Wallet出金          = Σ USD          [Settlement = t, Source Name = 'Rebate Withdrawal']
CRM出金            = MT4出金 + Wallet出金
TD出金             = Σ USD          [Completed = t, Status ≠ refuse]
——crm已出,TD未出    = Σ USD          [Settlement = t, Completed > t, Status ≠ refuse]
                    + Σ USD          [Settlement = t, Completed = 1/1/1970]
——调上日差异 (出金)   = -Σ USD         [Completed = t, Settlement < t, Status ≠ refuse]
CRM 入金（原币种）   = Σ Transaction  [Settlement = t]
CRM 出金（原币种）   = Σ OC           [Settlement = t]
实收（原币种）       = Σ Transaction  [Paid = t]
实出（原币种）       = Σ Transaction  [Completed = t]
——未打款            = Σ OC           [Settlement = t, Completed > t, Status ≠ refuse]
                    + Σ OC           [Settlement = t, Completed = 1/1/1970]
——手续费/转账费      = Σ Charges      [Completed = t]     (hanya USDT & USD)
——调上日差异 (原币种) = -Σ Transaction [Completed = t, Settlement < t]
本日 MT4+錢包淨入金  = MT4入金 + Wallet入金 - MT4出金 - Wallet出金
月累计              = akumulasi 本日 sepanjang bulan
合計                = jumlah antar currency
```

`OC` = *original currency*: untuk `USDT` dan `USD` mata uang aslinya memang USD, jadi
rumus mereka memakai kolom **USD**; currency lain memakai kolom **Transaction**.

Basis tanggalnya penting: MT4/CRM pakai **Settlement Date**, TD入金/实收 pakai
**Paid Date**, TD出金/实出 pakai **Completed Date**.

## Number parsing (`angka.py`, PR #26)

Every number a person types (upload form, CLI arguments) and every number cell
stored as text in an uploaded file is read by one function,
`angka.parse_number()`. Accepted:

| Kind | Examples |
|---|---|
| plain / decimal | `1234`, `1234.5`, `1234,5`, `.5` |
| scientific (Excel shortens long numbers) | `3.5E+09`, `3.5e9`, `3,5E+09` |
| Indonesian thousands | `3.500.000.000`, `3.500.000,50` |
| English thousands | `3,500,000,000`, `3,500,000.50` |
| negative | `-1234`, `(1,234)`, `1234-` |
| spaces / NBSP / currency | ` Rp 3.500.000 `, `IDR 3,5E+09`, `USD 12.50`, `12.50 USDT`, `$1,234` |

Rules for `.` and `,`:

1. Both appear: the **last** one is the decimal point (`1.234,5` and `1,234.5` = 1234.5).
2. One kind repeated: thousands (`3.500.000` = 3500000). Groups must be 3 digits.
3. One separator followed by 1–2 or 4+ digits, or after `0`, or in the mantissa of
   `E` notation: decimal (`377,23`, `0,500`, `1.2345`, `3,5E+09`).
4. One separator followed by **exactly 3 digits** (`1.234`) is ambiguous:
   - balances typed on the upload page and `--jwallet-opening` / the pasted channel
     table: **thousands** (`377.233` = 377233), as before;
   - file cells and rates: `.` is the decimal point and `,` is thousands
     (`1.234` = 1.234, `1,234` = 1234), as before;
   - a value marked `Rp` / `IDR` always uses thousands (`Rp 1.000` = 1000).

Anything else (`12abc`, `1.2.3`, `5%` in an amount field) is refused with the value
and the running version in the message.

## Segregated — monthly roll-up of the daily files (`dpm_segregated.py`, PR #27)

DPM menu **Segregated** (`/tool/segregated`, not on KVB). Upload the whole month
of daily segregated files (one per day, `.csv`/`.xlsx`/`.xlsm`, same layout every
day) plus the month's **Client Equity FX** file (required). Always uploaded in
chunks; 70 files / 12 GiB per run like Deal Segregator.

```
python3 dpm_segregated.py day01.csv ... day30.csv "Client Equity - FX.xlsx" -o Segregated.xlsx
```

Output: one `.xlsx` (download name `Segregated - Sep 2026.xlsx`):

| Sheet | Content |
|---|---|
| `Monthly Summary` | one row per account (+ currency): text columns (latest value), Days, First/Last date, every numeric column summed, `Balance`/`Equity` from the **last day**, `X (USD)` columns, `Check` |
| `Daily` | every daily row stacked with `Date` and the `X (USD)` columns (continues on `Daily 2`, ... past 1,048,575 rows) |
| `Verifikasi` | files, column mapping, checks (yellow = needs a look) |

Columns are matched by header (case / spaces / punctuation ignored):

- account: `Login`, `Account`, `Account ID`, `Account No`, `Login ID`, ... (required);
- currency: `Currency`, `CCY`, `Account Currency` (missing = all USD, flagged);
- day: `Date`, `Report Date`, `Data Date`, `Time`, ... in the rows, else the file
  name (`2026-09-01`, `20260901`, `01-09-2026`, `1 Sep 2026`; year-less `1 Sept`
  takes the FX file's year); neither = STOP;
- a header with `BALANCE` or `EQUITY`: last day's value (with `PREV`/`OPENING`/
  `START`: first day's value), never summed;
- price / rate / leverage / level / `%`: Daily only, not summed;
- volume / lots / deals / trades / count: summed, not converted;
- every other numeric column (any new one too): summed and converted;
- an existing `X (USD)` column next to `X`: recalculated from `X`;
- id and text columns (`Name`, `Group`, `Deal`, `...ID`): kept as text.

A column is numeric when every non-empty cell parses with `angka.parse_number`
(`-` counts as empty). A column with numbers and some non-numbers is not summed
and is flagged.

USD: `amount / rate` with the same lookup as Deal Segregator
(`deal_segregator.pembagi_usd`: exact date + currency, blank USD rate = 1). Each
daily row uses its own day's rate; Balance/Equity use the last day's value at the
last day's rate. A missing rate leaves the USD cell blank and yellow; an account
with any missing day has its monthly USD sums blank.

Flagged on Verifikasi / the `Check` column: missing FX rates (date, currency,
rows), the same date in two files (rows are added together), byte-identical files
(the second one is skipped), days of the month with no file, more than one month,
accounts missing on the last day, Balance/Equity blank or 0 on the last day,
file-name date different from the Date column.

Memory grows with the number of accounts, not rows: rows are aggregated as they
are read and spooled to a temp file next to the output for the Daily sheet.

## Kalau ada gateway atau rate baru

## Upload queue (PR #25)

- Each staged upload records its owner (`user` in `staging/<id>/manifest.json`).
- A new upload by the same account replaces that account's older staged or abandoned
  upload and its queue slot. The old tab gets "replaced by a newer upload" and stops.
  Other accounts' staged data is never touched.
- Your own running job is never cancelled: a run is a subprocess inside one gunicorn worker
  and has no stored PID, so it cannot be stopped safely. The new upload waits, with a link
  to the job, and starts automatically when the job finishes.
- When another account is busy, the notice names it: "Server sedang dipakai oleh <username>".
  Uploads staged before this change have no owner, so they get the generic notice.
- An upload that has sent no chunk for 5 minutes (`DW_UPLOAD_BLOCK_SECONDS`) stops blocking
  others. It is still deleted only after 15 minutes idle, so a retrying or offline browser can
  resume. Queue tickets expire 30 s after the last poll.
- The browser discards its upload when retries run out, when a file cannot be read, and on
  tab close (`pagehide` via `sendBeacon`, skipped for pages kept in the back/forward cache).

## KVB Deal Segregator — MT4 cent accounts and unreadable files (v1.36)

**MT4 account-type file.** Two layouts are accepted (any column order, any header case;
`.xlsx`/`.xlsm`/`.csv`):

| Layout | Columns |
|---|---|
| new | `account`, `GROUP`, `account_type` |
| old (still works, same result as before) | `account`, `account_type` |

Cent rule (`deal_segregator.ATURAN_CENT`): a login is **USC** (Commission, Fee, Swap and
Profit ÷ 100) when `account_type` is `CentAccount` **or** its `GROUP` contains
`cent`/`cents`/`USC` as a word (`real\Plus-10-cents`, `Plus-10-centsFM`,
`real\Pro-06-SL5-cents`). Words like `Percent`, `Accent` or `KBP-KK-CME` are not cent groups.
Every other login, and a login missing from the file, is USD. With a GROUP column the
Verifikasi sheet shows the rule, the counts (both / GROUP only / account_type only /
neither) and, in yellow, the logins that GROUP made USC (account_type alone would say USD)
and any CentAccount login whose GROUP is not a cent group (kept USC). A login listed twice
with the same currency is fine; two different currencies for one login is a STOP.

**Upload robustness.** In the browser each file is read (first and last 64 KB, one retry
after 1 s) as soon as it is picked, and read again right before upload. A file that cannot
be read (`NotReadableError`) or changed since it was picked (fingerprint mismatch)
is named in Indonesian and English with a **Pilih ulang file ini / Re-select this file**
button that replaces only that file; nothing is uploaded until it is fixed. The cause is
almost always that the file changed on disk after it was picked (re-exported or
re-downloaded with the same name, saved in Excel, synced by OneDrive/Google Drive or
online-only). The account-type file is now sent in the chunked upload too, so the
"file N of M" counter includes it. Sizes under 1 MB show in KB (no more "0 MB" for a
300 KB file).

## Partner Approval (Beta, v1.35)

Test-only, DPM-only. Sales fill the "Sales PartnerRequest" form at `/approval`
(the same fields and conditional rules as the Lark form). The admin approves or
rejects at `/approval/admin`. For **Agreement** and **Special Terms** requests,
approving fills the role's Word template, converts it to PDF, and creates a
one-time signing link (`/sign/<token>`, no login, valid 14 days). The partner
either signs on screen (draws, or types their name in a script font) or uploads a
signed copy. The request then waits as **Signed – Under Review** until the admin
marks it **Completed** or asks for a re-sign, which creates a new link. A
**Dowgrade** or **Remove - Exit** request is approved or rejected only; approving
one marks it Completed.

- The code is self-contained in `partner_approval/`, with two Flask blueprints
  and its own SQLite DB, so it can move to FinanceOS later. `app.py` only calls
  `partner_approval.register(app)`.
- **Who can use it:** only users with DPM access. A KVB-only user is sent to
  `/kvb`. Admin pages and actions are for admins only.
- **Agreement templates:** `partner_approval/agreement_templates/<ROLE>.docx`.
  `CM.docx`, `BM.docx` and `RM.docx` exist (v1.35). MIB, NCIB and RD have no
  template yet: approving one still works (the request is Approved, not
  blocked), with the note "Agreement template for <role> not ready yet", no
  signing link and a **Retry agreement** button for when the file is added.
  Special Terms is MIB-only, so a Special Terms approval makes no agreement
  until `MIB.docx` exists. See `agreement_templates/README.md`.
- **The company signature column is never filled**, not even after the partner
  signs. The partner's signature goes in the "SIGNED by the <role>" cell
  (Country Manager / Business Manager / Relationship Manager).

### Security (v1.34)

- **Links:** 256-bit random tokens. Lookup is by SHA-256 hash with a constant-time
  compare. A link is single-use, expires (`DW_SIGN_LINK_DAYS`), is revoked when
  a new link is made or the request is rejected, and only works while the
  request is Approved/Re-sign. The plain token is also kept so the admin can
  copy the link.
- **Brute force:** 20 unknown links or 30 sign/upload posts per IP in 15 minutes
  return 429 (counted in SQLite, so all gunicorn workers share the count). The
  IP is read from `CF-Connecting-IP`/`X-Real-IP`/`X-Forwarded-For`: bind
  gunicorn to `127.0.0.1` so these cannot be forged.
- **CSRF:** every admin/user POST needs the session token. The public sign and
  upload forms carry an HMAC of the link (`Origin` is useless there because of
  `no-referrer`).
- **Headers on `/sign/*`:** `no-store`, `Referrer-Policy: no-referrer`,
  `X-Robots-Tag: noindex`, `nosniff`, `X-Frame-Options: DENY` and a nonce CSP with
  `frame-ancestors 'none'` (the PDF and page images allow `'self'` so the page
  can embed them).
- **Uploads:** checked by content (PDF header + `%%EOF`, PNG/JPEG verified by
  Pillow, ≤ 60 MP, ≤ `MAX_UPLOAD`), saved as `signed_upload.<ext>` under
  `DW_APPROVAL_DIR` (never under `static/`), and served only to admins with
  `nosniff`, `no-store` and an explicit content type. Signed-file downloads are
  logged.
- **State machine:** status changes are checked on the server inside a
  `BEGIN IMMEDIATE` transaction, so a double click or two admins cannot approve
  twice. A form submission carries a one-time key, so a double submit creates
  one request.
- **E-mail:** addresses must fully match a strict pattern. Headers have CR/LF
  and control characters removed. User text is HTML-escaped in pages and e-mail.
- **Logs:** sign-page errors are logged as `/sign/***`. SMTP errors stored in the
  audit log have the password and link removed. Do not enable gunicorn's
  `--access-logfile` (it would contain the link), or redact `/sign/...` in it.
